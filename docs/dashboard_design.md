# ECデータ基盤 BIダッシュボード詳細設計（ドラフト）

## 0. 本書の位置づけ

本書は、EC購買データとGA4風行動ログを用いたポートフォリオ向けBIダッシュボードの設計提案である。最終仕様ではなく、実装コスト、サンプルデータの自然さ、Looker Studio／Tableau Publicの制約を確認しながら採否を決めるためのドラフトとする。

想定する主な評価ポイントは次のとおり。

- 経営、マーケティング、コンテンツ、CRM、EC運営など、利用部門ごとの意思決定を説明できる
- 売上などの結果指標だけでなく、行動ログから原因を掘り下げられる
- 指標定義、データ粒度、期間比較、フィルター、ドリルダウンが一貫している
- GCP版とAWS版で同じ論理モデル・KPIを再現し、クラウド間の実装力を示せる
- 派手なチャートの数ではなく、「異常の発見 → 要因分解 → 対象特定 → アクション」の分析導線を示せる

### 推奨する全体方針

公開版は、既存3ページに優先度P0の3ページを加えた**6ページ構成**を第一候補とする。P1以降は同一ワークブック内の発展ページ、またはポートフォリオ記事内の追加分析として切り出すと、情報過多を抑えやすい。

1. 全体KPI
2. デジタルマーケティング
3. コンテンツ貢献
4. CRM／LTV・RFM
5. コホート・リテンション
6. 購買ファネル・離脱

クロスセル、価格施策、在庫機会損失、オムニチャネルは有力だが、追加データを自然に生成できる場合に採用する案を推奨する。

### 共通の指標定義案

実装前に、少なくとも以下をデータ辞書で固定することを提案する。

| 指標 | 定義案・注意点 |
|---|---|
| 売上 | `gross_sales`（値引前）、`net_sales`（値引後・返品前）、`recognized_revenue`（返品控除後）を区別 |
| 注文数 | テスト・キャンセル注文を除外した `order_id` のユニーク数 |
| 購入者数 | 購入した `user_id` のユニーク数。匿名IDとの混同を避ける |
| CVR | 原則「購入セッション数 ÷ セッション数」。ユーザーCVRと併記する場合は名称を明示 |
| AOV | `net_sales ÷ orders` |
| ROAS | アトリビューション対象売上 ÷ 広告費。売上の帰属方式を明示 |
| CPA | 広告費 ÷ 新規顧客獲得数、または広告費 ÷ 注文数。両者を区別 |
| LTV | 観測期間内の返品控除後売上、粗利、注文回数を用途別に表示。将来予測値とは分離 |
| リテンション | 初回購入コホートのうち、各経過月に再購入した顧客の割合 |
| コンテンツ貢献 | ラスト接触、購入前閲覧、アシストのどの定義かを明示 |

# 1. ニッチ分析軸一覧（優先度付き）

## 1.1 優先度の判断基準

- **意思決定価値**：実在する部門が施策や運用を変えられるか
- **データ実現性**：現在の購買データ＋GA4風ログで無理なく再現できるか
- **訴求力**：モデリング、SQL、BI設計、計測設計の複合スキルを示せるか
- **実装負荷**：追加テーブルや複雑な可視化に対して得られる価値が十分か

P0を本編候補、P1を有力な拡張、P2を条件付きの発展テーマとする。

## 1.2 提案一覧

| 優先度 | 分析テーマ | 主な利用部門・問い | 現データでの実現性 | 追加データ／実装上の要点 | 提案理由 |
|---|---|---|---|---|---|
| P0 | LTV／RFMセグメント | CRM・経営：「優良、休眠予兆、新規顧客は誰か」「獲得チャネル別の質はどうか」 | 高 | 顧客別集計マート、粗利を扱うなら原価 | 購買履歴だけで成立し、単発CVだけでなく顧客価値を扱えることを示せる |
| P0 | コホート・リテンション | CRM・事業企画：「初回購入月／獲得チャネル別に再購入率が改善したか」 | 高 | 初回購入日、経過月、再購入フラグ | 時系列集計と母数管理の力量が見え、施策の短期・長期評価を分離できる |
| P0 | カート放棄／チェックアウト離脱 | EC運営・UX：「どの段階、端末、流入元、入力項目で落ちるか」 | 高～中 | `view_item`、`add_to_cart`、`begin_checkout`、フォーム段階イベントの計測仕様 | GA4行動ログの強みを最も生かし、改善箇所を直接特定できる |
| P1 | クロスセル／バスケット分析 | MD・商品企画：「一緒に買われる商品は何か」「セット販促候補は何か」 | 高 | 注文明細から商品ペア集計。支持度、信頼度、リフト | SQL能力と商品施策への接続を示せる。ただしSKU数が多いと可視化を絞る必要がある |
| P1 | 価格・クーポン・セール効果 | 販促・MD：「値引きで増分売上／粗利が生まれたか」「カニバリはないか」 | 中 | 定価、実売価、クーポン、セール期間、原価。可能なら対照群 | 割引率別CVRだけでは因果効果とはいえないため、比較設計を示すと評価が高い |
| P1 | 在庫・欠品による機会損失 | 在庫管理・MD：「閲覧需要があるのに買えないSKUは何か」 | 中～低 | 日次または時点在庫、入荷、欠品閲覧、再入荷通知 | 購買されなかった需要を行動ログから推定でき、データ統合力を示せる |
| P1 | 会員ランク別行動・育成 | CRM：「ランク上昇前の行動は何か」「特典が継続率に効くか」 | 中 | 会員ランク履歴、付与条件、特典利用 | 現在ランクだけで過去を集計すると未来情報混入になるため、履歴モデリングが見せ場になる |
| P1 | 商品・カテゴリ・季節性分析 | MD・仕入：「季節ごとの需要、売れ筋、曜日・時間帯の偏りは何か」 | 高 | 商品階層、カレンダー、可能なら原価・在庫 | 実装は容易で運用価値も高いが、一般的な売上分析との差別化には前年差や構成比変化が必要 |
| P2 | オムニチャネル | 店舗運営・経営：「ECと店舗の併用顧客は高LTVか」「会員登録や購買がチャネル間でどう移るか」 | 低（現状） | 店舗、POS、店舗会員登録、チャネル横断ID、店舗マスタ | 実務的かつ訴求力は高いが、現在のデータ範囲を超える。追加するなら独立した拡張として丁寧に設計したい |
| P2 | アトリビューション／チャネル遷移 | マーケティング：「購入までにどのチャネルがアシストしたか」 | 中 | セッション列、タッチポイント順序、帰属ルール | ラストクリック偏重を避けられるが、サンプルでは“因果”ではなく“配分ルール”と説明する必要がある |
| P2 | 検索ゼロ件・サイト内検索分析 | EC運営・コンテンツ：「需要はあるが商品が見つからない検索語は何か」 | 中 | 検索語、検索結果数、検索後の閲覧・購入 | 顧客の明示的需要を捉えられる。検索ログを自然に生成できる場合は比較的低コスト |
| P2 | 返品・キャンセル分析 | CS・品質・MD：「返品率が高い商品／理由／顧客群はどこか」 | 低（現状） | 返品明細、返品理由、返金日、数量 | 売上の質や商品品質まで扱えるが、注文状態だけで返品を代用しない方がよい |

## 1.3 本編採用の提案

### 本編に推奨：P0の3テーマ

LTV/RFM、コホート、ファネルは、現在の2本柱である購買と行動ログをバランスよく使える。3ページを通じて、次の一連の問いを表現できる。

> どこから顧客を獲得したか → どこで購入を阻害しているか → 獲得後に優良顧客へ育ったか

### デモ映えを強める場合の第7ページ候補

クロスセル／バスケット分析を推奨する。注文明細だけで実装でき、ネットワーク図や商品ペアランキングで視覚的な差別化ができる。ただしネットワーク図は探索の入口とし、必ず数値表と併用する。

### 業務データ基盤らしさを強める場合の第7ページ候補

在庫・欠品機会損失を推奨する。イベント、商品、在庫スナップショットを結合するため、データ基盤としての広がりが出る。一方、機会損失売上は実績値ではなく推定値なので、計算仮定とレンジを明示する。

# 2. ページ別ダッシュボード構成案

## 2.1 全ページ共通のUX・レイアウト

### 推奨キャンバス

- PC閲覧を主対象に、横幅 1,440px 前後の固定レイアウトを基本とする
- 12カラムのグリッド、上部にページ名・説明・更新日時、その下に共通フィルターを配置する
- 1画面目で「状況」、2画面目で「要因」、3画面目で「明細・対象」を追える縦スクロール構成を推奨する
- 重要KPIは5～7枚まで。色は状態や意味に割り当て、チャートごとに無関係な色を増やさない

### 共通フィルター案

- 期間、比較期間（前期／前年同期）
- デバイス、地域
- 新規／既存顧客
- source / medium / campaign
- 商品カテゴリ

ページ固有のフィルターは別段に配置し、すべてのフィルターが全チャートに影響するように見せない。フィルター適用範囲をラベルまたはコンテナで明示する。

### 共通インタラクション

- チャート選択によるクロスフィルター
- ツールチップに指標定義、前年差、母数を表示
- 商品、キャンペーン、コンテンツから詳細ページまたは外部URLへドリルスルー
- 小さい母数は非表示または警告表示
- 更新日時、データ対象期間、主要な除外条件をフッターに常設

### ビジュアルの選択原則

- 達成状況：KPIカード＋目標差
- 時間変化：折れ線、面グラフ、スパークライン
- 構成比較：100%積み上げ棒、ドットプロット
- 順位：横棒、条件付き書式付き表
- 分布：ヒストグラム、箱ひげ図
- 関係：散布図
- 段階離脱：ファネル＋段階別表
- コホート：ヒートマップ
- 経路：Sankey。ただし主要経路に限定し、表で補完

円グラフ、ゲージ、ワードクラウド、3Dチャートの多用は避ける案を推奨する。面積や角度より位置と長さの方が比較しやすく、限られた画面で情報密度を保てるためである。

## 2.2 Page 1：全体KPI（経営・事業責任者向け）

### 意思決定

売上・顧客・集客・収益性のどこに変化があり、どのページへ掘り下げるべきかを短時間で判断する。

### レイアウト案

**上段：エグゼクティブサマリー**

- KPIカード：返品控除後売上、注文数、購入者数、CVR、AOV、新規顧客数、ROAS
- 各カードに前期比／前年比、目標差、20～30点程度のスパークライン
- 正負の色はKPI特性に応じる。返品率やCPAは低下が好ましいため、単純な増減色にしない

**中段：トレンドと分解**

- 左 8カラム：日次／週次の売上・注文数コンボチャート。前期または前年を薄色で重ねる
- 右 4カラム：売上差異のウォーターフォール  
  `Traffic × CVR × AOV` の寄与分解、またはチャネル別増減寄与

**下段：診断**

- チャネル別の売上・広告費・ROASを示すバブル散布図（x=広告費、y=ROAS、size=売上）
- カテゴリ別の売上、粗利率、前年比を条件付き書式で示すランキング表＋スパークライン
- 地域別売上の塗り分け地図。地域施策がデータ上存在しない場合は優先度を下げ、デバイス／新規既存の構成比に置換
- 自動インサイト風の短文領域：「売上前年差の主因」などを事前計算したルールベース文で表示できると訴求力が高い

### 実装可否

- **Looker Studio**：KPI、期間比較、コンボ、散布図、地図、表は標準機能で実現可能。ウォーターフォールは標準対応状況に依存するため、積み上げ棒で代替、またはコミュニティ可視化を検討する。公開ポートフォリオでは外部可視化の安定性に注意。
- **Tableau Public**：すべて実現可能。ウォーターフォール、Viz in Tooltip、パラメータによる指標切替、ダッシュボードアクションとの相性がよい。

## 2.3 Page 2：デジタルマーケティング（獲得最適化）

### 意思決定

どのチャネル／キャンペーンへ予算を寄せるか、流入量・質・費用のどこに問題があるかを判断する。

### レイアウト案

**上段**

- KPIカード：セッション、購入セッション、CVR、広告費、新規顧客CPA、ROAS
- 帰属モデルの表示：「Session last non-direct」など。切替を実装する場合はラスト接触と線形配分程度に絞る

**中段**

- 左：日次の広告費と帰属売上、ROASのコンボチャート。キャンペーン開始・セール日を注釈
- 右：チャネル別バブル散布図（x=CPA、y=CVRまたはROAS、size=新規顧客数）。目標線で4象限化
- チャネル別ファネル：Session → View item → Add to cart → Checkout → Purchase。絶対数と段階CVRを併記

**下段**

- source / medium / campaign の階層ランキング表：セッション、CVR、顧客数、売上、広告費、CPA、ROAS、前年差、スパークライン
- デバイス × チャネルのCVRヒートマップ
- 発展：購入までのチャネル遷移Sankey。上位経路＋Otherに集約し、パス長とコンバージョン率の表を併設

### 設計上の注意

- 広告費の日次粒度とイベント／注文の粒度を直接結合すると、費用が多重計上される。日付・キャンペーン粒度の集計マートで接続する
- セッションの流入元と注文の帰属方法を明記する
- ROASが高いが件数の少ないキャンペーンを過大評価しないよう、件数または信頼区間相当の警告を表示する

### 実装可否

- **Looker Studio**：標準ファネルは機能差があるため、横棒またはコミュニティ可視化で代替可能。Sankeyはコミュニティ可視化依存になりやすく、公開安定性を優先するなら遷移表にする。
- **Tableau Public**：ファネル、四象限散布図、Sankeyを計算フィールド／パスで実現可能。ただしSankeyの保守負荷は高いので補助チャート扱いを推奨する。

## 2.4 Page 3：コンテンツ制作（コンバージョン貢献）

### 意思決定

どのコンテンツが認知・回遊・購入の各段階に貢献し、何を更新／再利用／廃止すべきかを判断する。

### レイアウト案

**上段**

- KPIカード：コンテンツ閲覧セッション、エンゲージメント率、コンテンツ経由商品閲覧率、アシスト購入数、アシスト売上
- コンテンツ種別、公開日、著者、content_group、ランディング／途中接触のフィルター

**中段**

- 左：公開日を起点にしたコンテンツ別累積閲覧・アシストCVの時系列
- 右：散布図（x=閲覧数、y=購入貢献率、size=アシスト売上、color=content_group）。高閲覧低貢献／低閲覧高貢献を識別
- コンテンツ接触 → 商品閲覧 → カート → 購入のファネルを、接触あり／なしで比較

**下段**

- コンテンツランキング表：タイトル、公開日、閲覧、平均エンゲージメント時間、離脱率、商品クリック、直接CV、アシストCV、売上、公開後経過日
- コンテンツ → 商品カテゴリの関連ヒートマップ
- 上位コンテンツの閲覧後ページ遷移。Tableauでは簡易Sankey、Looker Studioでは遷移元／遷移先のランキング表を推奨

### 設計上の注意

- 「閲覧後に購入」と「閲覧したため購入した」は異なる。画面上では「貢献」または「関連」と表現し、因果効果と断定しない
- 古い記事が累積閲覧で有利にならないよう、公開後30日、90日、日次平均を用意する
- ラストページだけでなく購入前N日以内の接触をアシストとして定義し、重複配分ルールを固定する

### 実装可否

- **Looker Studio**：主要構成は可能。購入前接触の判定はBI内計算ではなくDWH側でマート化する。
- **Tableau Public**：散布図選択からランキング／遷移へのハイライト、Viz in Tooltipが有効。

## 2.5 Page 4：CRM／LTV・RFM（P0追加案）

### 意思決定

顧客を価値と休眠リスクで分類し、維持、再活性化、育成施策の対象を決める。

### レイアウト案

**上段**

- KPIカード：顧客数、平均観測LTV、リピート率、購入頻度、平均購入間隔、休眠予兆顧客数
- 基準日、初回購入期間、獲得チャネル、会員ランクのフィルター

**中段**

- RFMセグメント構成：Champions、Loyal、Potential Loyalist、New、At Risk、Hibernating等の顧客数／売上構成比
- RFM散布図：x=Recency、y=Monetary、size=Frequency、color=segment。外れ値の影響を抑えるため対数軸または上限クリップを検討
- セグメント遷移：前月 → 当月の遷移行列ヒートマップ。Sankeyは上位遷移だけを補助表示

**下段**

- セグメント別比較表：顧客数、売上、粗利、AOV、購入頻度、平均購入間隔、直近購入日、主獲得チャネル
- 獲得チャネル別の90／180／365日LTV曲線
- アクション対象表：休眠予兆顧客群を個人情報なしの匿名セグメント集計で表示

### 設計上の注意

- RFMスコアは分析基準日時点のデータだけで計算し、未来の購入を混ぜない
- 五分位スコアは分布が変わると境界が変わる。固定閾値と相対スコアのどちらを使うか説明する
- Public環境では個人単位の閲覧を避け、最小集計人数を設ける

### 実装可否

- **Looker Studio**：事前計算済みRFMマートがあれば実現可能。セグメント遷移はヒートマップ風ピボット表が安定。
- **Tableau Public**：散布図、セットアクション、遷移ハイライトに適する。密度が高い場合はHexbinも候補。

## 2.6 Page 5：コホート・リテンション（P0追加案）

### 意思決定

獲得施策や初回購入体験の改善が、その後の再購入と顧客価値に結びついたかを判断する。

### レイアウト案

**上段**

- KPIカード：30／90／180日再購入率、2回目購入までの日数中央値、12か月累積LTV
- コホート定義（初回購入月）、指標（顧客リテンション／売上リテンション／累積LTV）の切替

**中段**

- 中央を大きく：コホートヒートマップ。行=初回購入月、列=経過月、色=再購入率、ラベル=率、ツールチップ=母数
- 右：選択コホートのリテンション曲線。全体平均との差を重ねる

**下段**

- 獲得チャネル別のリテンション曲線（上位5＋Other）
- 初回購入カテゴリ別の180日LTV／再購入率ドットプロット
- コホート明細表：初回顧客数、M1/M3/M6率、累積注文数、累積売上、前年差

### 設計上の注意

- 直近コホートには未成熟期間があるため、観測できないセルを0として塗らず、NULL／ハッチング相当で表示する
- 月次再購入率（その月に購入）と累積再購入率（一度でも再購入）を混同しない
- 月初／月末起点の偏りを避けたい場合は30日単位コホートも用意する

### 実装可否

- **Looker Studio**：事前集計した `cohort_month × months_since_first × dimension` マートをピボット表＋条件付き書式で表現可能。
- **Tableau Public**：ヒートマップ、選択コホート連動曲線、指標パラメータ切替を自然に実装できる。

## 2.7 Page 6：購買ファネル・離脱（P0追加案）

### 意思決定

購入までのどの段階に摩擦があり、どの端末・ブラウザ・流入元・商品群から改善すべきかを特定する。

### レイアウト案

**上段**

- KPIカード：商品閲覧セッション、カート投入率、チェックアウト開始率、購入完了率、カート放棄率、フォームエラー率
- デバイス、ブラウザ、OS、流入チャネル、新規／既存、商品カテゴリのフィルター

**中段**

- 左 7カラム：View item → Add to cart → Begin checkout → Shipping → Payment → Purchase のファネル。段階間CVRと離脱数を表示
- 右 5カラム：比較セグメントの段階CVR差分を示すドットプロットまたは横棒。例：モバイル対デスクトップ
- 日次の主要段階CVR管理図または折れ線。サイト改修日・障害日を注釈

**下段**

- デバイス × 段階の離脱率ヒートマップ
- エラーコード／入力項目別の発生数、影響セッション、購入率ランキング
- 離脱商品カテゴリ／SKUランキング：閲覧、カート投入、欠品表示、購入、推定離脱影響
- セッションリプレイは扱わず、匿名集計された経路を利用

### 設計上の注意

- ファネルは「同一セッション内か」「順序を必須とするか」「同一商品か」を仕様化する
- イベント再送や重複を `event_id` で排除する
- GA4風ログにshipping/payment段階がない場合は無理に生成せず、4段階ファネルから開始する

### 実装可否

- **Looker Studio**：ファネル集計マートを用意すれば実現可能。段階切替など複雑な状態管理は限定的。
- **Tableau Public**：パラメータで比較セグメントを選び、選択した段階から下位表へアクションフィルターをかけられる。

## 2.8 Page 7候補A：クロスセル／バスケット分析（P1）

### レイアウト案

- KPI：複数商品注文率、平均点数、クロスカテゴリ注文率、上位ペア売上
- 商品カテゴリ／商品ペアのネットワーク図：ノードサイズ=注文数、線幅=同時購入数、色=カテゴリ
- 商品A選択時の商品Bランキング：共起注文数、支持度、信頼度、リフト、ペア売上
- 商品A購入あり／なしのAOV・再購入率比較
- カテゴリ間の共起ヒートマップ

ネットワーク図はTableau Public向きで、Looker Studioでは商品ペア表とヒートマップを中心にする案が安定する。リフトが高くても件数が少ないペアが上位化しやすいため、最低支持度を設ける。

## 2.9 Page 7候補B：価格・セール効果（P1）

### レイアウト案

- KPI：値引率、クーポン利用率、セール売上、粗利率、セール後リピート率
- 日次の売上・粗利・CVRにセール期間を帯で表示
- 割引率帯別のCVR、数量、粗利率ドットプロット
- セール対象／非対象、前年同曜日、施策前後の比較
- 商品別の売上増分と粗利増減を示す四象限散布図
- クーポン別ランキング表

単純な施策前後差は季節性や広告流入の影響を含む。ポートフォリオでは「記述的比較」と明示し、可能なら類似商品の対照群を使った差の差（Difference-in-Differences）を別途SQL分析として提示する案が有効。

## 2.10 Page 7候補C：在庫・欠品機会損失（P1）

### レイアウト案

- KPI：欠品SKU数、欠品商品閲覧数、再入荷通知数、推定機会損失売上、在庫回転
- 欠品率と商品閲覧需要の四象限散布図
- SKU別の在庫数・閲覧・販売数の時系列
- カテゴリ × 日付の欠品ヒートマップ
- 推定機会損失ランキング：欠品閲覧セッション × 通常時CVR × 通常時AOV

推定値は点推定だけでなく、保守／標準／強気の3シナリオまたは範囲で示すことを提案する。代替商品購入があるため、単純推定が過大になり得ることも注記する。

## 2.11 Page 7候補D：オムニチャネル（P2）

### レイアウト案

- KPI：EC売上、店舗売上、チャネル併用顧客率、EC→店舗／店舗→EC転換、会員登録数
- EC／店舗／併用顧客の売上・頻度・LTV比較
- 会員登録チャネルから初回・2回目購買チャネルへのSankey
- 店舗地図：店舗売上、EC配送売上、商圏内会員数
- 店舗 × ECカテゴリの売れ筋差分ヒートマップ
- 顧客チャネル遷移のコホート表

魅力的なテーマだが、同意済み会員IDによるID統合、店舗POS、店舗マスタが必要になる。匿名IDを恣意的に同一人物へ結び付ける設計は避ける。

# 3. テーブル設計への追加・変更提案

## 3.1 設計原則

既存の原始／中間テーブルを直接BIへ接続するだけでなく、以下の3層を分ける案を推奨する。

1. **Raw/Staging**：生成元の形を保存し、型・重複・命名を整える
2. **Core**：ディメンショナルモデル。注文、注文明細、イベント、ユーザー、商品、キャンペーン費用
3. **Mart/Semantic**：BIの粒度に合わせた日次KPI、ファネル、RFM、コホートなど

BigQueryとAthenaで同じ論理列名・指標定義を持たせ、クラウド固有の物理最適化だけを分けると比較しやすい。

## 3.2 既存テーブルへの変更案

### `dim_users`

追加候補：

- `user_sk`：DWH内部キー
- `user_id`：ログイン会員ID（匿名化）
- `registration_at`、`registration_channel`
- `first_order_at`、`first_order_id`
- `acquisition_source`、`acquisition_medium`、`acquisition_campaign`
- `country`、`region`、`prefecture`
- `membership_rank_current`（現在値。履歴は別表）
- `valid_from`、`valid_to`、`is_current`（属性履歴を扱う場合）

`user_pseudo_id` と会員 `user_id` は1対1とは限らないため、dim_usersへ単純に同居させるよりIDブリッジを設ける案が安全である。

### `dim_products`

追加候補：

- `product_sk`、`product_id`、`sku_id`
- `product_name`、`brand`
- `category_l1`、`category_l2`、`category_l3`
- `list_price`、`standard_cost`
- `launch_date`、`discontinued_date`
- `is_active`
- `valid_from`、`valid_to`、`is_current`

カテゴリや定価が変わる想定ならSCD Type 2を検討する。ポートフォリオでは全項目をSCD化せず、価格履歴は別ファクトに分ける方が説明しやすい。

### `fact_orders`

追加候補：

- `order_status`、`ordered_at`、`completed_at`、`cancelled_at`
- `user_id`、`session_id`
- `currency`
- `gross_sales`、`discount_amount`、`tax_amount`、`shipping_amount`、`net_sales`
- `coupon_code`
- `order_channel`（将来のEC／店舗拡張用）
- `is_first_order`

注文ヘッダーと明細の売上列の整合ルールをテストする。広告費と同様、注文ヘッダー額を明細結合後にSUMして多重計上しないようにする。

### `fact_order_items`

追加候補：

- `order_item_id`
- `product_id`、`sku_id`
- `quantity`
- `unit_list_price`、`unit_selling_price`、`unit_cost`
- `item_gross_sales`、`item_discount_amount`、`item_net_sales`
- `promotion_id`
- `returned_quantity`（返品を実装する場合は返品ファクトを正とする）

### `fact_events`

GA4 Export準拠を示しつつ、BI利用用にはネストをフラット化した中間モデルを作る案を推奨する。

追加・明確化候補：

- `event_id`：重複排除用
- `event_date`、`event_timestamp`
- `event_name`
- `user_pseudo_id`、`user_id`
- `session_id`、`session_number`
- `page_location`、`page_path`、`page_title`
- `content_id`、`content_group`、`content_type`
- `product_id`、`item_list_name`
- `source`、`medium`、`campaign`、`gclid`相当
- `device_category`、`browser`、`operating_system`
- `country`、`region`
- `engagement_time_msec`
- `form_step`、`error_code`（離脱分析を採用する場合）
- `search_term`、`search_result_count`（サイト内検索を採用する場合）
- `is_engaged_session`、`is_conversion_event`

流入元はイベント時点、セッション時点、初回ユーザー獲得時点を別列または別モデルに分ける。これらを1つの`source`で兼用すると分析結果が曖昧になる。

### `dim_campaign_cost`

名前は `fact_campaign_cost_daily` の方が実態に合う可能性がある。広告費はディメンションではなく日次の数値ファクトであるため。

追加候補：

- `cost_date`
- `platform`、`account_id`
- `source`、`medium`、`campaign_id`、`campaign_name`
- `ad_group_id`、`creative_id`（必要な粒度まで）
- `impressions`、`clicks`、`cost`
- `currency`

キャンペーン名は変更され得るため、結合キーには可能ならIDを使う。

## 3.8 データ品質テスト案

- 主キーの一意性・NOT NULL
- 注文ヘッダー金額と明細合計の一致
- `purchase`イベントと注文の照合率
- セッション内イベント時刻の妥当性
- ファネル順序逆転・重複イベント率
- キャンペーン費用の結合不能率
- 商品・ユーザーの参照整合性
- 売上、数量、割引、原価の非負／許容範囲
- コホート経過月が負にならないこと
- 直近コホートの未観測セルが0埋めされていないこと
- IDブリッジで同時点に矛盾する対応がないこと

## 3.9 BigQuery／Athenaの物理設計案

### BigQuery

- イベント・注文・日次ファクトは日付パーティション
- `user_pseudo_id`、`session_id`、`campaign_id`、`product_id`など、主要な絞り込み／結合列をクラスタ候補とする
- BI Engine等の有料機能を前提にせず、マートと抽出でスキャン量を抑える
- `require_partition_filter` を検討する

### Athena

- S3上はParquet＋圧縮、日付パーティションを基本とする
- 小さすぎるファイルを多数作らず、日次処理後に適切なサイズへまとめる
- BI接続が頻繁に生データ全走査しないよう、CTAS等で日次マートを生成する
- GCP版とのKPI差分検証用に、同一期間・同一フィルターの集計結果を比較する

## 3.10 Looker Studio／Tableau Publicへの提供方式

- **Looker Studio**：BigQueryのBIマートへ接続し、可能な限り単一データソース内で完結させる。ブレンドは広告費多重計上やフィルター不整合が起きやすいため限定する。
- **Tableau Public**：公開物に認証情報や個人粒度データを含めない抽出ファイルを使用する。抽出作成時点と更新頻度を表示する。
- 両BIでチャート表現が完全一致することより、KPI定義と分析ストーリーが一致することを優先する。

## 3.11 実装優先順位の提案

最小限で高い完成度を狙う場合、以下の順序が比較的安全である。

1. 指標辞書、イベント仕様、粒度、帰属方式を確定
2. `dim_date`、`fact_sessions`、日次KPIマートを追加
3. Page 1～3を実装し、売上・セッション・広告費の整合を検証
4. ファネルマートとPage 6を実装
5. RFMスナップショット、コホートマートとPage 4～5を実装
6. GCP版とAWS版の同一KPI差分テスト
7. P1から1テーマだけ追加し、深さを補強
8. 公開用データの匿名化、母数制御、表示速度、モバイル時の代替導線を確認

最終的には、ページ数よりも各ページに「誰が、何を判断し、次にどのアクションを取るか」を1文で示し、ダッシュボード上の操作でその問いに答えられる状態を完成条件とする案を提案する。
